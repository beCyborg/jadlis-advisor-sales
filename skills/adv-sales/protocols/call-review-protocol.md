# Call Review Protocol — режим CALL

Петля разбора реального звонка — главная ценность совета: книги дают язык, поведение
меняет разбор конкретных реплик. Findings без анкора в транскрипте недействительны.

## Phase A — нормализация транскрипта (главная сессия, ДО workflow)

1. Получить транскрипт (текст/файл). **Гейт разметки сторон**: если реплики не размечены
   по говорящим — попросить пользователя разметить или подтвердить автоopределение;
   не удалось → вслух деградировать CALL до VERDICT-по-саммари.
2. Нормализовать в `{WORK_DIR}/transcript.md` с анкорами:
   ```
   [T01] ПРОДАВЕЦ: …
   [T02] КЛИЕНТ: …
   ```
   Один анкор = одна реплика (длинные монологи резать на [T07a]/[T07b] по смыслу).
   Это ground truth: claims скептиков и находки советников проверяются по нему.
3. Собрать DEAL_PROFILE (deal-profile-gate.md, экран 1) + контекст звонка (какой по
   счёту, цель, что было до).
4. **Конфиденциальность**: транскрипт остаётся в WORK_DIR на время прогона. Копия в
   `{MEMORY_DIR}/Звонки/` — только по явному подтверждению пользователя и
   после редактирования имён/компаний. Без подтверждения WORK_DIR удаляется целиком.

## Схема находки (findings)

Каждый советник возвращает findings по схеме:

| Поле | Что |
|---|---|
| `anchor` | `[Tnn]` — реплика, к которой относится находка (обязательно, существующий анкор) |
| `whatHappened` | что произошло в этой реплике, нейтрально |
| `missed` | что было упущено / какой сигнал проигнорирован |
| `betterMove` | конкретная альтернативная реплика/ход (с citation-тегом линзы) |
| `severity` | critical / significant / minor |

## Ростер CALL

Базовый: gap, spin, khalsa, blount-objections, jolt, story.
+voss — если в звонке живые переговоры о цене/условиях; +qsl — если профиль mid/high ACV
и комитет. Гейты deal-profile применяются до запуска.

## Скептики (3 именованные линзы на каждый claim куратора)

1. **Факт транскрипта**: находка опирается на то, что РЕАЛЬНО сказано в [Tnn]? Прочитай
   анкор в transcript.md. Приписанное, домысленное, вырванное из контекста → refuted.
2. **Контрфактуал**: если бы продавец сделал предложенный betterMove, правдоподобно ли
   лучше? Какой риск нового хода? Post-hoc-умность («после боя все генералы») → refuted.
3. **Тип сделки**: находка валидна для ЭТОГО DEAL_PROFILE? Совет из enterprise-плейбука
   на транзакционном звонке → refuted.

Ротационная 4-я линза — **сикофантность**: не является ли находка просто согласием с тем,
как продавец сам оценил свой звонок в контексте?

## Формат вердикта CALL

```markdown
# Разбор звонка: {дата/клиент-псевдоним}

> [!info]- {DEAL_PROFILE, советников N/M, ledger-сводка}

## Вердикт одной строкой {самое дорогое место звонка}

## Хронология критических моментов
| Анкор | Что произошло | Что упущено | Severity | Линзы |

## ТРИ хода на следующий звонок  ← ЖЁСТКИЙ ЛИМИТ: ровно ≤3
1. {ход + точная формулировка + тег + к какому моменту прошлого звонка привязан}

## Что было сделано хорошо {2–3 пункта с анкорами — честно, не для баланса}

## Разногласия линз {где линзы читают один момент по-разному}

## Где совет мог просто согласиться {сикофантность-проверка}
```

**Лимит ≤3 хода — предохранитель**: разбор, из которого выходят с десятью поправками,
не меняет следующий звонок. Материал, не влезший в тройку, остаётся в хронологии.

## Пост-обработка

- Ходы из «ТРИ хода» — кандидаты в Плейбук (`{MEMORY_DIR}/Профили/adv-sales.md`, секция
  Playbook) — заносить ТОЛЬКО по явному подтверждению пользователя.
- Смоук-прогоны CALL — только на синтетическом или отредактированном транскрипте.
